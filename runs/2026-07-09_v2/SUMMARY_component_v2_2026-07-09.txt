THREE METHOD BUGS FOUND AND FIXED (all three change the partition)
------------------------------------------------------------------
B1  Step 0 deduplicated multi-HSP pairs by MAXIMUM PERCENT IDENTITY, which selects
    short, high-id, statistically insignificant fragments over the true best
    alignment. Example: n157<->n160 (Q7WXF6) — step0 kept the 69.6%-id / e=2.7e-5 /
    40-bit HSP and discarded the 63.1%-id / e=4.07e-78 / 282-bit one, then failed
    the pair on e-value. 11 strong edges were dropped this way.
    -> Step 0's archived "42 components / 3,170 edges" is reproduced EXACTLY by the
       max-id rule, and by no other rule. The 42 was an artifact.
    -> Its reported "SPLIT: v1 comp 3 sheds Q7WXF6" was entirely this artifact.
    Correct rule (best-scoring HSP: max bits, ties -> min e-value):
       fwd only    : 3,179 edges / 41 components
       symmetrized : 3,178 edges / 42 components   <- adopted (paper: 3,195, -0.5%)
    The paper's edge count is CLOSER to the corrected 3,178 than to step0's 3,170.

B2  usearch e-values scale with database size: E = K*m*N*2^-bits, N = total db
    letters. Verified on 4,986 shared v1-v1 pairs between the 213- and 492-node
    runs: alignments identical (median d(pct_id) = 0.000, median d(bits) = 0.000)
    while median log10(e_492/e_213) = +0.3537 vs predicted log10(N2/N0) = +0.3538.
    A raw e < 1e-5 on the 492-node db is therefore a STRICTER criterion than the
    paper's, and would sever edges between two unchanged sequences merely because
    PAZy grew. Raw thresholding gives 44 v1-induced components instead of 42.
    -> Fix: renormalize every e-value to the 213-node search space
       (N_REF = 74,254 letters; scale = 0.442781) before thresholding.
    -> Only then does the plan's Step 2 requirement hold: the v1-induced subgraph
       of the 492-node graph is PARTITION-IDENTICAL to the standalone 213-node
       reference (42 blocks, identical membership).

B3  `-allpairs_local` is ORIENTATION-DEPENDENT: the earlier FASTA sequence is always
    the query, and the HSP returned depends on that role. m0275/m0438 aligns at
    29.8% id / 195 bits one way and 35.8% id / 179 bits the other — straddling the
    30% cutoff. 8 boundary edges flipped between the 213- and 492-node node orders;
    7 of them sit at 29.2-30.4% id. The graph was a function of FASTA order.
    -> Fix: align every pair in both orientations (run on the reverse-ordered FASTA)
       and keep the best-scoring HSP. Graph is now order-invariant.

Also fixed: 27 delta nodes carry a sequence but NO accession (33 such pull records),
so D4's "smallest member accession" rule was resolving on blank strings. Added a
fallback chain accession -> uniprot -> pdb -> all_accessions -> "pazy:<id>".

Residual (does not change the partition): pair m0214<->m0487 aligns at 30.4% id /
e=1.5e-18 / 84 bits in the 213-node run but is not reported by usearch in EITHER
orientation of the 492-node run. No per-query hit cap is in play (max 312 hits,
attained once). This is a genuine usearch allpairs_local coverage miss.

CAVEATS
-------
- 22 of 45 models are singleton HMMs, built from one sequence; their coverage is
  vacuous and they cannot be validated. They can seed a search but carry no
  family-level evidence.
- Coverage is measured by searching each HMM against its own training members,
  so it is optimistic by construction (this mirrors the paper's HMM-coverage
  filtering, which is likewise self-referential).
- The 42-component target is conditional on the 2026-06-30 PAZy snapshot matching
  the paper's 2024-12-19 retrieval.
- Input data is a rough/demo snapshot; the `cath` column and 33 sequence-less
  records are incomplete.
