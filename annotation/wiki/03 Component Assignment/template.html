Component Assignment

PETadex searches outward from families of enzymes, not from single enzymes, so the way the plasticome is split into families decides what gets searched for. We call these families components.

We aligned the cluster centroids of the plasticome against each other and linked any two that share at least 30% amino acid identity. Each connected group is one component. This gives components. One α/β-hydrolase component, the family of IsPETase and LCC, holds centroids, and centroids are not linked to any other.

What the map shows

Most of what is known about plastic-degrading enzymes sits in one component. C001, the α/β-hydrolase family of IsPETase and LCC, holds 337 of the 609 plasticome enzymes and 327 of the 376 that act on PET. The other 272 enzymes are spread over 45 components, and 27 of those have only one or two enzymes. Research has followed a few successful PET hydrolases and their close relatives, so the known diversity is narrow. PETadex searches outward from every component, not only C001, to find plastic-degrading enzymes beyond this one family.

Each enzyme's component is listed in the plasticome explorer, which can also filter by component.

Why components

The next steps of PETadex search public sequence databases for relatives of the plasticome. Those searches, and the profile models that filter their results, are built per family. A component is our working definition of a family: a set of plasticome enzymes joined to each other by chains of clear sequence similarity.

The plasticome cannot be treated as one family. It contains several unrelated folds (see CATH Assignment), and sequences from different folds do not align in any meaningful way. Components split it into groups that can each be aligned and searched on their own.

Inputs

The input is the cluster centroids from clustering the plasticome at 90% identity. Clustering first keeps near-identical enzymes from adding hundreds of redundant alignments. Cluster members are not aligned here; each joins the component of its centroid, which it matches at 90% identity or more.

Each centroid becomes one node of the graph, identified by the MD5 hash of its sequence (letters only, upper case). Identical sequences from different records are therefore one node. All centroid sequences are distinct, giving nodes and residues in total.

All-against-all alignment

Every centroid was aligned to every other with USEARCH v11, using local alignment and keeping every hit, however weak:

usearch -allpairs_local combined.fasta -acceptall -userout combined_pairs.tsv \
    -userfields query+target+id+evalue+bits
usearch -allpairs_local combined_rev.fasta -acceptall -userout combined_rev_pairs.tsv ...

-allpairs_local aligns each sequence only against those after it in the file, so a pair can come out differently depending on which sequence is the query. The search is therefore run twice, once on the file reversed, and both outputs are pooled. This gave alignments over distinct pairs. Each pair keeps the alignment with the highest bit score (ties go to the lower E-value), so every pair is judged on one alignment.

No threshold is applied during the search. All filtering happens afterwards, on the saved alignments, so the cutoff can be changed and the components recomputed without aligning again.

When two centroids are linked

Two centroids are linked if their best alignment has both:

  • at least 30% amino acid identity, and
  • E-value below 10−5, as reported for this search (a database of residues).

The E-value rule removes short, chance alignments that reach 30% identity over a few dozen residues. The identity rule removes long alignments between distant relatives whose E-values are small only because the sequences are long. of the aligned pairs pass both.

Figure 3 is recomputed from combined_pairs.tsv and combined_rev_pairs.tsv with the same best-HSP rule as step23_graph.py, so the bars above 30% add up to the run's edges.

Connected components

The links form a graph, and each connected piece of it is one component: two centroids are in the same component if a chain of links joins them, even when they are not linked directly (single linkage). Components are numbered by size, largest first.

We use connected components instead of assigning each centroid to its single best match. Best-hit assignment breaks up families that are continuous: a chain A–B–C, where A and C are too distant to align, can end up as two groups depending on which of B's matches scores higher. Families like the α/β-hydrolases are exactly such chains, with distant members joined through intermediates.

Choosing 30%

The cutoff decides how coarse the components are. We re-ran the partition at other identity cutoffs on the same alignments and scored each against the CATH superfamily of each centroid's catalytic domain. A component is "mixed" if it contains more than one catalytic superfamily.

Identity cutoffComponentsSingle centroidsLargestMixed componentsCentroids in their component's majority fold

30% is the loosest cutoff at which no component mixes folds. Below it, the five subtilisin-family protease centroids join an α/β-hydrolase component. Above it, components only break into smaller pieces of the same fold: nothing is gained in purity, and each family is split into more, smaller searches.

The sweep is computed in extract_data.py on this run's alignments. The fold labels come from 02 CATH Assignment, which was itself split into catalytic and accessory domains using these components, so the purity score is a consistency check, not an independent one. logan-plasticome-figure/ssn/README.md has the same kind of table for the 609-sequence map (99.8% at 30%).

Components and folds

Components are finer than folds. Every component contains one catalytic fold, but one fold can be spread over many components. The α/β-hydrolase fold alone spans components: its members are related by structure, but many are too distant in sequence to be linked at 30%. The fold groups of the forest figure gather components back together by fold.

USEARCH or DIAMOND

Two steps depend on an alignment engine: clustering at 90% (which sequences become centroids) and this all-against-all alignment (how centroids group into components). To see how much the components depend on that choice, we ran all four combinations of USEARCH and DIAMOND on the same input, with the same linking rule.

ClusteringAlignmentCentroidsAligned pairsLinksComponentsSingleLargest

The aligner barely matters. With the clustering held fixed, 42 of 47 components are identical with either aligner, and six or seven centroids cross a component boundary on links close to the cutoff. DIAMOND reports fewer aligned pairs but passes about 120 more links.

The clusterer matters only through the centroids. With the USEARCH aligner, the 295 centroids both clusterers chose keep exactly the same components; with DIAMOND, two move. The real difference is which and how many centroids there are (404 against 413).

In every combination the second to fifth largest components have 45, 19, 16 and 14 centroids. Only the large α/β-hydrolase component changes size, from 218 to 233, as distant members join or leave it. The partition is therefore stable to the choice of engine, and we use USEARCH for both steps.

The 2×2 ran on an earlier 610-row union (2026-08-05), which is why it shows 413 and 404 centroids and 47 to 48 components, against 411 and 46 in the final run. The final run uses the USEARCH/USEARCH arm. Per-cell detail: runs/2026-08-05.diamond/REPORT_diamond_vs_usearch.md.

Checks

  • Reproducing the original PETadex components. The same code, applied to the 213 sequences of the original PETadex seed set, gives the published 42 components (3,178 links). This engine check is step 0 of the standalone driver.
  • Old component labels are respected. centroids carry a component label from the original set. The labels are compared afterwards and never used to build the partition. No old component is split across two new ones ( splits).
  • Identical sequences cannot be separated. Nodes are sequence hashes, so two records with the same sequence are always in the same component.

Back to 609 enzymes

Each of the 609 plasticome enzymes takes the component of the centroid of its 90% cluster: are centroids themselves and the rest are cluster members. The result is one table with a row per enzyme, giving its cluster, its centroid, its identity to that centroid and its component. This is the table 02 CATH Assignment uses to separate catalytic from accessory domains, and the component column is what later steps search by.

About Figure 1

Figure 1 is drawn for readability, not as the assignment itself. It shows all 609 enzymes, not only the centroids, and uses DIAMOND with an extra rule that an alignment must cover at least half of the shorter sequence. That rule cuts some long-range links inside the α/β-hydrolase family, so the map shows 56 components instead of 46. Almost every component of the map lies inside one component of the assignment. The exceptions are three α/β-hydrolase enzymes that sit with a different α/β-hydrolase group on the map than in the assignment.

Limitations

  • One link is enough. Single linkage joins two groups through one alignment. This is what keeps continuous families together, and also what would merge two families if a single spurious alignment passed both rules.
  • No coverage rule. A link can come from an alignment over part of each sequence, such as a shared accessory domain. The fold check above found no component that mixes catalytic folds at 30%.
  • Components are not folds. Distant members of one fold land in separate components. Fold-level grouping comes from CATH, not from this step.
  • Single centroids. centroids have no link. Each is still searched on its own, but from a family of one.

Reproducing

Component assignment is step 3 of the plasticome pipeline. One driver runs it with the steps around it:

./pipeline_run.bash <run-name> --engine usearch --to 6
# step 3 alone, on an existing cluster table
ENGINE=usearch "lib/03 alignment/run_from_clusters.sh" runs/<run>/02-clusters.tsv

USEARCH v11 is a Linux binary and runs in Docker. The step writes 03-alignment.tsv (the cluster table with a component_id column), the per-enzyme table 05-union-with-components.tsv, and every intermediate (alignments, links, component members, run statistics) under 03-alignment.intermediates/.

The pipeline's default engine is now DIAMOND; the final run used --engine usearch, so the command above names it. Step 0 (the 213-sequence check) runs in lib/03 alignment/run.sh, not in run_from_clusters.sh. Add the GitHub link once the repository is public.
